# ADR 012: модульное рабочее пространство проекта

**Статус:** принято  
**Дата:** 2026-08-28

## Контекст

Проекты отличаются по масштабу и процессу. Фиксированная карточка заставляет каждый проект показывать одни и те же крупные блоки, а карточный редактор сметы плохо подходит для 50–70 строк. При этом текущие `Order`, `WorkTask`, `ProjectEstimate*`, файлы, контакты и тайминг уже являются рабочими источниками истины и участвуют в аналитике, XLSX и операционных сценариях.

Нужна гибкость уровня рабочего пространства без дублирования данных и без одномоментной опасной переписи всего проектного домена.

## Решение

1. Шапка проекта остаётся фиксированной и содержит ключевые поля, ответственного, участников и read-only финансовую сводку.
2. Тело проекта становится 12-колоночной сеткой типизированных виджетов с разрешёнными размерами.
3. `ESTIMATE` и `ORDERS` обязательны; остальные виджеты добавляются, скрываются и переставляются пользователем.
4. `ProjectWidget` хранит только layout, видимость, версию и UI-config. Бизнес-данные продолжают жить в существующих доменных таблицах.
5. Скрытие виджета не удаляет данные. Виджет может быть восстановлен с прежней конфигурацией.
6. `Project.ownerUserId` становится явным ответственным. Создатель фиксируется отдельно, участники хранятся в `ProjectMember`, а ответственный всегда является участником.
7. Свободная доска использует отдельные типизированные items и ссылки на задачи, заявки, файлы и сметные элементы. Бинарные файлы остаются в Storage.
8. Смета остаётся нормализованной и типизированной, но получает табличный UI. Произвольные helper columns не участвуют в финансах без явного безопасного mapping.
9. Изменения сохраняются оптимистически через очередь на уровне сущности, client IDs, idempotency keys и revisions. Полная перезагрузка проекта после обычной правки запрещена.
10. Внедрение выполняется аддитивными миграциями и независимыми feature flags. Legacy UI сохраняется до окончания parity-периода.

## Последствия

- Проекты можно адаптировать к конкретному процессу, не создавая несколько жёстких типов.
- Layout и содержимое становятся независимыми: UI-настройка не способна изменить финансы или удалить заявку.
- Появляются новые таблицы участников, layout и свободной доски, а также ревизии и batch API.
- Новые типы виджетов требуют registry contract, Zod schema, version migration и states.
- Табличный редактор и свободная доска внедряются только после базового workspace shell и проверки сохранения.
- Независимая смета остаётся отдельной сущностью по ADR 007 и получает общий grid только после его стабилизации в проектах.
- Откат интерфейса выполняется feature flag без destructive rollback БД.
