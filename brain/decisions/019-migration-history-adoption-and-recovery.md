# ADR 019 — Сверка исторических SQL Editor-миграций без повторного пересчёта данных

Дата: 10.10.2026. Статус: принято.

## Контекст

Рабочая схема менялась через Prisma и SQL Editor. Журнал содержал 31 успешную миграцию и одну незавершённую, хотя актуальные таблицы/поля уже существовали. Запуск всех pending SQL повторял бы ALTER/CREATE и старые пересчёты данных.

## Решение

1. Сохранить consistent pg_dump public-схемы/данных и отдельный точный ACL/RLS rollback. Восстановить дамп в локальный PostgreSQL 17; сверить количество строк всех 87 таблиц.
2. Повторить полную цепочку миграций на пустой БД. Удалить UTF-8 BOM из `20260615120000_project_estimate_line_internal_expenses`: этот невидимый префикс вызывал SQL syntax error. Успешного production-записа для этой миграции не было; checksums остальных успешных записей проверены без изменения.
3. Сверить Prisma diff и нативный каталог PostgreSQL: колонки/defaults, порядок enum labels, индексы, CHECK/PK/UNIQUE/FK с validation. Разница числового enumsortorder не существенна при одинаковом порядке labels.
4. Семь checklist-строк без WorkTask, препятствовавших FK, по явному разрешению владельца сохранить целиком в `maintenance.OrphanedChecklistArchive` (JSONB) и убрать из рабочих таблиц. Сохранить связанные assignee rows, если есть. Архив вне Data API, RLS без публичных policies; ни существующие задачи, ни проекты/заявки не удалять.
5. Additive/idempotent `20261010123000_reconcile_manual_schema`: недостающие FK задач с проверкой строк, индекс primary estimate, два имени усечённых индексов, два лишних updatedAt default. Без бизнес-пересчётов.
6. После успешной проверки копии и рабочей схемы принять отсутствующие исторические записи через официальный `prisma migrate resolve --applied`. Это фиксация проверенного текущего состояния, **не утверждение о повторном выполнении каждой исторической data migration**.

## Последствия

Можно разворачивать пустую БД обычной цепочкой и применять новые миграции контролируемым `migrate deploy`. Старые массовые UPDATE рейтингов, частей суток, порядка карточек и смет не повторяются: сохраняются текущие рабочие значения.

Для другой существующей БД необходимо повторить независимую сверку; автоматическое «пометить всё применённым» запрещено. Архивирование ограничено максимумом 7 бесхозных пунктов и проверяет точность копии до DELETE. Восстановление требует вернуть/создать родительскую задачу и проверить связанные IDs; слепой INSERT нарушит включённый FK.

CI каждый раз проверяет replay на пустом PostgreSQL и Prisma drift. Backup из этой процедуры не включает auth/storage schemas или файлы buckets; они не менялись. Для полного disaster recovery нужны отдельные backup Storage и приватной maintenance-схемы.
