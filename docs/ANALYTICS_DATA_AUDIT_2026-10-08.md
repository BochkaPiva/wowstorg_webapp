# Проверка достоверности аналитики — 08.10.2026

## Вывод

Расхождение лидеров на присланных скриншотах воспроизведено запросами к подключённой рабочей БД через действующий `getAdminAnalyticsData`. Причина конкретного расхождения — разные периоды вкладок, не разные формулы выручки клиентов. Более широкий период до 07.09.2026 точно воспроизводит лидеров обзора; период до 23.07.2026 точно воспроизводит таблицу клиентов. Период самого обзора на первом скриншоте не виден, поэтому его фактическое сохранённое значение в браузере не утверждается.

Одновременно обнаружены реальные проблемы полноты, календарной агрегации и соответствия Excel интерфейсу. Финансовую аналитику пока нельзя считать полностью согласованным отчётом.

Аудит не изменяет бизнес-записи, продуктовый код, правила дат, статусы или суммы. Нет деплоя/пуша. Созданы только этот отчёт и read-only диагностический скрипт `.impeccable/review/analytics-data-audit.cjs`.

## Что именно считается сейчас

1. **Выручка клиента за период** = суммы завершённых проектов + суммы самостоятельных закрытых заявок. Это уже агрегированный показатель двух источников, не только проекты.
2. **Проекты:** только `mode = FULL`, с заказчиком; сумма всех смет с `includeInProjectTotals = true`, не исключительно `isPrimary`. При отсутствии учитываемых смет используется расчёт чернового реквизита. В финансовом факте только `COMPLETED`; в прогнозе — активные, неархивные, неотменённые. Даты мероприятия должны пересекать выбранный период.
3. **Самостоятельные заявки:** `projectId = null`, статус `CLOSED`, окончание аренды в периоде. `issuedQty`, а при отсутствии — `requestedQty`; сохранённые ставки и коэффициенты, скидки, услуги и клиентский налог из общего pricing helper.
4. **Связанные заявки** отдельно в выручку клиента не прибавляются: принадлежат проекту и должны попасть в одну из учитываемых смет. Иначе финансовый результат не восстанавливается автоматическим повторным сложением.
5. **Прогноз клиентов** в текущей таблице — только активные проекты. Активные самостоятельные заявки присутствуют в общем прогнозе обзора, но не разнесены по клиентам.
6. **Прибыль** — расчёт после заданных внутренних расходов и условных налогов, а не бухгалтерская чистая прибыль. Закупка собственного парка, зарплаты/постоянные расходы и амортизация автоматически в эту прибыль не включаются.
7. **LTV:** текущая таблица показывает результат выбранного периода, не пожизненный LTV. Архивные Excel-снимки сверки не добавляются в оперативную выручку; это правильная граница ADR 008. Банковские оплаты здесь тоже не учитываются.

## Подтверждённые недостатки

### P1 — разные периоды выглядят как противоречивые отчёты

Независимость периодов предусмотрена исходным ТЗ, но при переходе пользователь ожидает детализацию того же обзора. Особо заметно у лидеров и перехода «Все проекты».

Рекомендация: общий отчётный период обзора/проектов/клиентов/реквизита **либо** явное действие «Показать за период обзора», которое переносит даты при drill-down. Бонусы и сверку оставить независимыми. Не менять это поведение скрытно: потребуется согласование изменения прежнего сценария.

### P1 — завершённые проекты без дат молча отсутствуют в периодном факте

`admin-analytics.ts:332` исключает проекты без обеих дат. Найдены четыре завершённых проекта с учитываемыми сметами:

| Проект | Клиент | Рассчитанная выручка |
|---|---|---:|
| Тимбилдинг БАКС | БАКС | 52 300,00 ₽ |
| Провокация_Формула1_27.06.26 | Провокация | 39 445,00 ₽ |
| ПРОЛЕУМ Значки | Пролеум | 19 317,70 ₽ |
| Информационные технологии ГПН | Газпром | 129 375,00 ₽ |
| **Всего без даты** | | **240 437,70 ₽** |

Это не доказательство принадлежности всех четырёх выбранному году/месяцу. Без дат нельзя честно приписать их периоду. Не использовать название/дату создания как молчаливую замену.

Рекомендация: отдельный индикатор «Не распределено по датам», список исходных проектов, ручное подтверждение дат; затем пересчёт. При завершении проекта проверять наличие финансовой даты. Нет автоматической корректировки записей в этом аудите.

### P1 — фактическая выручка одного проекта учитывается в двух соседних месяцах

Реальный проект «День города Панда Проджект»: 31.07–01.08.2026, 195 559,80 ₽. По правилу пересечения полная выручка входит и в июльский, и в августовский фактический итог. При сложении отдельных месячных отчётов возникает повторный учёт, хотя в едином отчёте за оба месяца проект один.

Рекомендация: разделить правила даты для факта и прогноза. Факт — одна согласованная дата признания (например, окончание мероприятия); прогноз — пересечение интервала. Если нужна разбивка по дням, она должна распределять сумму, не повторять её. Выбор даты — решение владельца продукта, не произвольное исправление агента.

### P1 — график, KPI и Excel расходятся по месяцу проекта

`admin-analytics.ts:1264` относит проект к окончанию мероприятия. `admin-analytics-xlsx.ts:266` — к началу. `completeAnalyticsTimeline` не отображает точки вне запрошенных месяцев.

Воспроизведение генерацией настоящего XLSX в памяти и повторным чтением ExcelJS:

| Проверка | Июль | Август |
|---|---:|---:|
| Факт KPI | 409 504 ₽ | 974 148 ₽ |
| Факт графика выбранного месяца | 213 944 ₽ | 974 148 ₽ |
| Excel, строка соответствующего месяца | 409 503,80 ₽ | 778 588,49 ₽ |

В августовском Excel дополнительно появилась строка **июля** на 195 559,80 ₽ — вне выбранного интервала. Разрыв не объясняется округлением: это перенесённый между месяцами проект Панды.

Рекомендация: единый датированный финансовый факт для KPI, клиентов, динамики и Excel. Проверять равенство общего итога сумме месяцев и отсутствие дат вне отчётного периода.

### P1 — таблица «Спрос и окупаемость» не содержит все использованные позиции

`admin-analytics.ts:607–611` возвращает лишь топ-20 по количеству и топ-20 по выручке. UI в `AnalyticsSections.tsx:54–59` объединяет эти два рейтинга с позициями, имеющими закупочную цену, и называет результат общей таблицей.

За 01.01–08.10.2026 в закрытых самостоятельных заявках использована **81** уникальная позиция. В объединённой таблице **33** позиции; **48** использованных не представлены вообще. Количество для части присутствующих позиций неизвестно, хотя исходные строки в БД есть. Поиск и страницы это не исправляют — данных нет в ответе.

Рекомендация: полноценный item-level read-model за период; топ-20 оставить только лидерам. Спрос по всему складу и самостоятельную финансовую выручку обозначать раздельно: заявки проектов нельзя дублировать в общих деньгах, но их физические выдачи важны для спроса.

### P2 — разное округление даёт расхождение даже в одинаковом периоде

До 23.07: обзор **587 535 ₽**, сумма клиентского факта **587 534 ₽**, динамика **587 534 ₽**. Источники округляются на уровне клиента/месяца/блока до рублей раньше финального сложения (`admin-analytics.ts:653,1042,1192,1331`).

Бонусы: августовский пул 83 067 ₽, на каждого 41 534 ₽; две отображаемые доли дают 83 068 ₽. Это ошибка распределения округлённой суммы на рубль, не неправильный процент.

Рекомендация: считать в копейках до финального отображения; единый общий total; доли распределять с учётом остатка. Не подгонять один показатель под другой потерей точности.

### P2 — названия и методология отстают от реальной модели

- `hasPrimaryEstimate` фактически означает наличие любой учитываемой сметы, не основной.
- «Средняя смета» рассчитывается как средний итог **проекта** с учитываемыми сметами, не средний отдельный документ. В одном проекте может быть несколько учитываемых смет.
- Excel-методология (`admin-analytics.ts:1363`) говорит о дате **создания** проектов, хотя фильтр по датам мероприятия.
- Доход клиента из проектов и заявок скрыт в раскрытии; число проектов = 0 не означает отсутствие заказов клиента. Нужен состав результата и число самостоятельных заявок.
- Excel «Внутр.» использует `internalSubtotal`, но прибыль дополнительно учитывает `cashInternalCostTax`. Колонки без явного дополнительного расхода не объясняют всю разницу.

Рекомендация: согласованный словарь показателей во всех вкладках/Excel; «Средний бюджет проекта», «Учитываемые сметы», явное разделение источников выручки.

### P2 — «Валовая прибыль» реквизита не является прибылью за период

Формула `revenue - purchasePricePerUnit × currentTotalQty` вычитает полную стоимость текущего парка из выручки выбранного периода. За проверенный период только у **3** позиций задана цена: стоимость 58 088 ₽, выручка 30 815 ₽, отображаемая «валовая прибыль» −27 273 ₽. Это не убыток склада и не расход закупки данного периода. Историческая стоимость закупки/парк на дату отчёта не фиксируются.

Рекомендация: назвать метрику «Выручка периода минус стоимость парка» либо убрать её из прибыльных KPI; «ROI периода» трактовать только как условное сравнение выбранной выручки с текущим закупом, не истинный lifetime ROI. Excel подставляет выдачи **0** при отсутствии позиции в топ-20 (`admin-analytics-xlsx.ts:431`) — заменить данными полной таблицы, а не предполагать ноль.

### P2 — ограниченный список рисков используется как полный

`admin-analytics.ts:1113` обрезает `risks` до 30; UI берёт оттуда KPI «Требуют внимания» и фильтр «С рисками». На текущих проверенных данных лимит не достигнут (2/2), но при 31+ рисков число и таблица станут неполными.

Рекомендация: считать KPI/фильтр по полному `projects.rows[].risks`, ограничивать только краткий список обзора.

### P2 — сверка требует одинакового охвата и явной даты снимка

`reconciliation/route.ts:102–122` сравнивает всю сумму импортированного файла с полным фактом сайта за **период сохранённого снимка**, а не только суммы сопоставленных строк. «Расходы сайта» = выручка − расчётная прибыль, включая условные налоги. Сопоставление означает совпадение сущности, не равенство финансов.

Изменение периода шапки не меняет выбранный сохранённый снимок (`AnalyticsReconciliation.tsx:28–43`); подпись его собственных дат нужна рядом с итогами, не только в селекторе. Исходные Excel-снимки остаются отдельно, что соответствует ADR 008.

Рекомендация: два явно названных режима — «Итоги всего периода» и «Только сопоставленные работы»; собственный период снимка в карточке сравнения; определение расходов/налогов. Настоящий внешний файл владельца в этом аудите не загружался, его содержимое/полнота не сертифицированы.

## Что подтвердилось корректным

- Клиенты обзора и таблицы используют одну агрегацию при одинаковых датах; оба присланных набора чисел воспроизведены.
- По 11 неотменённым проектам с учитываемыми сметами за 01.01–08.10 сверены **и выручка, и прибыль** аналитики с `buildProjectEstimateReadModel`: дельты 0. Сюда входят 10 завершённых и один активный.
- Связанные заявки исключаются из самостоятельного результата: нет повторного прибавления проектного реквизита к клиентской выручке. Это не отменяет отдельную проверку распределения каждой заявки по сметам.
- Отменённые проекты не увеличивают финансовый факт/прогноз; активные не подмешиваются к факту.
- В проверенной БД нет двух неслитых карточек с одинаковым нормализованным именем и ненулевыми деньгами; нет денежных строк на уже слитых карточках. Семантические дубли с разными именами так не исключаются.
- Базовые pricing/проектные формулы/клиентский presentation helper/парсер сверки: 21 тест в четырёх файлах прошёл. Они не проверяют календарную согласованность всего read-model, и найденные реальные дефекты этим набором не покрыты.

## Рекомендуемый следующий этап (после согласования)

1. Зафиксировать одну дату финансового факта проекта. Сохранить интервальное пересечение для прогноза. Для проектов без дат показать неполноту, не назначать им месяцы автоматически.
2. Построить общий реестр финансовых работ: тип/ID источника, customerId, дата факта, выручка/расходы/налоги/прибыль в копейках, состояние качества. Не требуется вводить бухгалтерскую оплату или менять сметы ради отчёта.
3. Из этого реестра получать обзор, клиентские итоги, месяцы, бонусы и Excel. Тесты на соседние периоды, проект 31.07–01.08, несколько смет, связанную заявку, отсутствие дат, точные суммы до копейки.
4. Клиентская таблица: **общая выручка факта / из проектов / из самостоятельных заявок / прогноз отдельно**. Количество работ и исходные проекты/заявки — в раскрытии. Lifetime-метрика — отдельное явно названное значение, если нужна, без смешения с прогнозом.
5. Полные таблицы реквизита/рисков; отдельные ограниченные лидеры. Исправить смысл окупаемости и полный состав расходов.
6. Согласовать даты между основными вкладками или переносить их при переходе из обзора, оставить бонусы/сверку независимыми. Уточнить copy/методологию и проверить интерфейс после исправления данных.

Impeccable использован для проверки понятности/целостности показателей, не для нового визуального редизайна. Полная повторная оценка accessibility/theming/responsive здесь не проводилась; финансовый вывод не подменяется оценкой дизайна. Для последующей UI-работы: `clarify` (названия и периоды), `harden` (неполнота и сверка), затем `polish`.

```powershell
node .impeccable/review/analytics-data-audit.cjs
node .impeccable/review/analytics-data-audit.cjs --details
node .impeccable/review/analytics-data-audit.cjs --boundaries

```

Скрипт использует существующую конфигурацию окружения, не печатает ключи/URL подключения, выполняет только чтение. XLSX проверяется в памяти, без загрузки файла в БД. Суммы — состояние БД на момент аудита, не гарантированно неизменяемый бухгалтерский снимок. Исторические даты/оплаты/внешние накладные не восстанавливались.
