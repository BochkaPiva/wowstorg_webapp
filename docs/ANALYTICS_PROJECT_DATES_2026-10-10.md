# Даты завершённых проектов в аналитике

## Решение

Дата закрытия не обязательно является датой мероприятия. По запросу владельца завершённые проекты без дат временно признаются по календарному дню закрытия в Омске. Приоритет: окончание мероприятия → начало → закрытие. Закрытие берётся из `archivedAt`, а при его отсутствии — из последнего реального перехода журнала в `COMPLETED`. Создание, последнее редактирование и название проекта не используются.

В аналитике есть общий список «Уточните даты мероприятия», не ограниченный выбранным периодом. Кнопка «Уточнить даты» открывает компактное окно около строки проекта. Оно доступно и для архивных завершённых проектов. Реальные начало/окончание имеют приоритет над временным закрытием; после сохранения перечитываются все закэшированные периоды, включая независимый период бонусов. Для уже датированных завершённых проектов даты также можно корректировать во вкладке «Проекты».

Дата проекта «Спорт_зоны» в рабочей БД **не изменялась**: известен сентябрь, но точный день не предоставлен. Пользователь выбирает реальные даты в интерфейсе. Даты сентября в browser QA являются исключительно демонстрационными.

## Безопасность

- Новый `PATCH /api/projects/[id]/event-dates` требует WOWSTORG и принимает только даты и ожидаемые прежние значения.
- Только `COMPLETED`; существующий общий API по-прежнему запрещает изменения архивных проектов.
- Строгая Zod-валидация календарных дат и порядка диапазона.
- Compare-and-set защищает от перезаписи одновременной коррекции коллеги. Изменение дат и журнал с автором выполняются в одной транзакции.
- Статус, архив, сметы, заявки и резервы не изменяются. Миграция не нужна.
- Активные проекты без дат и завершённые без записанного закрытия остаются вне финансовых итогов.

## Проверки

- `npm test -- --silent`: 324 теста / 55 файлов. Покрыты приоритет дат, границы суток/месяцев в Омске, повторные завершения, фильтрация периода, согласованность клиентов/диаграмм/Excel/бонусов, авторизация и ограничение нового API, конфликт правок и идемпотентный повтор.
- `npm run build`: production build и TypeScript проходят.
- Scoped ESLint для изменённых TypeScript-файлов: проходит.
- Browser QA на 1440 и 390 px: окно помещается в экран, конец автоматически подхватывает начало, конфликт сохраняет форму, успешное сохранение обновляет отчёт и ранее закэшированный независимый период, архивный проект остаётся доступным для коррекции, Escape возвращает фокус. Ошибок страницы и горизонтального переполнения нет. Все API перехвачены локально; QA не изменяет рабочую БД.
- Реальная БД проверена только чтением через существующий read model; Excel построен и разобран в памяти. Суммы обзора, клиентов, помесячной динамики и Excel совпали:

| Период | Выручка завершённых работ |
|---|---:|
| 01.01–08.10.2026 | 2 616 020,30 ₽ |
| 01.01–09.10.2026 | 2 670 070,30 ₽ |
| 01.09–30.09.2026 | 772 929,87 ₽ |

Разница 54 050 ₽ между первыми двумя периодами соответствует временному учёту «Спорт_зоны» по закрытию 09.10.2026. В сентябрьском отчёте проект появится после указания реальных сентябрьских дат. Эти суммы — снимок проверки, не гарантированные будущие значения.

Скрипты: `.impeccable/review/analytics-event-dates-audit.cjs` (read-only DB) и `analytics-event-dates-ui-qa.cjs` (synthetic UI/API). Реальная запись коррекции в production в ходе проверки не выполнялась; атомарность/CAS проверены кодом и route-тестами с DB mock, а не нагрузочным concurrency-тестом БД.

Использованы impeccable/clarify для компактного контекстного ввода и ясного обозначения временного источника даты; verification для разделения реальной финансовой проверки и синтетического сценария записи; React best practices для проверки hooks, управления фокусом и загрузкой. Новая документация API/env сгенерирована, реестр транзакций и ADR 016 обновлены.
