# Студия КП V2 — состояние внедрения

Дата: 08.10.2026. Пять рабочих срезов утверждённого V2, не вся спецификация целиком.

## Реализовано

- Общий список последних 100 КП с разделением на проектные/временные; из каталога запускается создание временного КП.
- Единая студия: outline разделов → состав → контекстный инспектор. На телефоне инспектор расположен перед составом; используется общий вертикальный скролл.
- Каталог в инспекторе загружается по запросу. Фото показываются целиком; доступны поиск, категории, добавление и ручная услуга.
- Копии вариантов, основные/альтернативные/дополнительные услуги, количество, клиентская цена, внутренний расход, клиентский комментарий.
- Явное сохранение формы с revision/CAS; конфликт 409 сохраняет поля, блокирует запись до загрузки актуальной версии. Переключение контекста требует подтверждения отказа от несохранённых полей.
- Итог считает только основной состав; «по запросу» не подменяется нулём, цены «от» обозначают предварительность.
- Клиентский вид и браузерная печать/PDF без расходов, контактов, маржи, внутренних заметок и служебных ошибок.
- Проектный виджет — компактная сводка и переход в студию. Существующие проектные КП используют тот же read model.
- Временное КП превращается в проект с переносом существующего дерева, не копированием. API также позволяет присоединение к пустому проекту, но UI присоединения ещё нет.
- Перенос основного состава в смету использует существующий идемпотентный endpoint и не заменяет строки сметы.
- Customer merge учитывает временные КП. ADR 015 и реестры обновлены.

### Второй этап: каталог → КП

- Каталог показывает целые фотографии, краткое описание, до трёх услуг с ценами и прямым действием «В новое КП». Контакты и внутренние заметки убраны из карточек.
- Контекстная немодальная панель: фотографии, полный список услуг, контакты, заметки; явное редактирование подрядчика и создание/редактирование услуги в том же месте. Модель цены управляет полями: диапазон показывает две границы, «по запросу» не требует фиктивного нуля.
- Серверный поиск/категории и keyset-подгрузка по 24 подрядчика, сортировка `isActive DESC, name ASC, id ASC`, cursor привязан к фильтрам. Публичного доступа нет: оба GET требуют WOWSTORG. Paged read не выбирает контакты, заметки и внутренние расходы; детали загружаются отдельно. Старый непагинированный API сохранён для совместимости.
- Подбор в студии использует тот же пагинированный поиск. Во время смены запроса предыдущие запросы отменяются, устаревшая дополнительная страница игнорируется.
- Запуск с услуги показывает, что именно добавится; POST получает только `seedOfferId`, а актуальные цена, категория, описания и фото snapshot читаются сервером в существующей Serializable-транзакции. Недоступная услуга не создаёт пустое КП молча.
- Единственная объяснимая подсказка следующего шага: структура → отсутствующая цена основного состава → пустой раздел → выбор основного состава → вступление → клиентский вид. Не меняет КП, бюджет или доступность подрядчиков автоматически; это не полноценный preflight.
- Сетевые ошибки освобождают busy, сохраняя поля; PATCH 409 блокирует форму до явной загрузки актуальных данных. Отмена закрытия/смены контекста сохраняет черновик. При неудачной загрузке фото после создания карточки сообщаем о частичном успехе, не предлагаем создавать дубль.
- Для этого этапа дополнительных изменений схемы БД нет. Миграция первого этапа всё ещё обязательна для временных КП.

## Третий срез: отмена и восстановление — 08.10.2026

- Серверные компенсирующие команды для оформления КП, добавления/удаления разделов и услуг, изменения цен/количества/включения и создания варианта. Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z и Ctrl+Y; рядом две компактные SVG-кнопки. В полях остаётся обычная отмена набранного текста браузером.
- UUID receipts/hash исключают повторное применение запроса при потерянном ответе. Сервер хранит delta только изменившихся записей, а не клиентскую замену документа. Исходные ID, приватные поля, фотографии-снимки и surviving links переноса восстанавливаются; строки сметы не откатываются.
- После network/5xx новые правки заблокированы до проверки того же UUID. Запрос и несохранённые поля переживают перезагрузку в версионированном локальном журнале пользователя/КП. Восстановление полей требует явного действия и совпадающей revision; при расхождении можно скачать локальную копию, но нельзя молча перезаписать сервер.
- Undo/redo хранит последние 50 команд и переживает reload при совпадении revision. После загрузки чужой новой версии история сбрасывается. CAS, проверка автора и проверка новых потомков не позволяют удалением родителя стереть независимые правки коллег.
- Добавлена отдельная additive-миграция `20261008120000_proposal_command_receipts`; применение к рабочей схеме подтверждено при подготовке релиза 08.10.2026.
- Это пока явные одиночные операции, не optimistic batch queue. Полноценное сравнение/слияние конфликтов, polling/presence и редактирование без глобального busy остаются следующими задачами.

## Четвёртый срез: управление порядком — 08.10.2026

- Разделы переставляются за ручку в структуре слева; услуги — за ручку в составе. Линия показывает вставку перед/после, пункт структуры принимает услугу в конец раздела. Наведение не пишет данные; Escape, pointercancel и потеря фокуса отменяют жест.
- Есть кнопки выше/ниже и стрелки клавиатуры на ручке. На телефоне кнопки доступны постоянно, имеют цель 44px; структура расположена компактным вертикальным списком. Перенос в другой раздел доступен также в инспекторе услуги.
- `MOVE_SECTION` / `MOVE_ITEM` выполняются в той же Serializable/CAS/UUID-транзакции и автоматически попадают в undo/redo. Сервер проверяет владение и принадлежность одному варианту; чужой anchor запрещён. ID, цены, приватные поля, фото и связь переноса не пересоздаются, смета не изменяется.
- Несохранённые формы требуют подтверждения перед перемещением; read-only, 409, recovery и неподтверждённый запрос блокируют перенос. Повторное положение не отправляет новый запрос из UI.
- Дополнительная миграция этому срезу не нужна; обе ранее подготовленные миграции остаются обязательными перед production. Сравнение вариантов, шаблоны и серверный PDF не входят в этот срез.

## Пятый срез: сравнение вариантов — 08.10.2026

- Отдельный режим «Сравнить варианты» рядом с составом и клиентским видом. До трёх выбранных вариантов: колонки — варианты, строки — разделы. На телефоне сравнение становится последовательными блоками с повторённым названием варианта, без сжатия таблицы и горизонтального overflow страницы.
- Первая колонка — точка сравнения; её можно поменять без серверной записи. «Только различия» скрывает одинаковые разделы. Есть понятные состояния одного варианта, недостаточного выбора и совпадающего состава, прямой вход в редактирование и клиентский вид выбранного варианта.
- Сопоставление разделов по нормализованному названию и порядковому вхождению одинакового имени; fuzzy matching и наследование ID не предполагаются. Переименование раздела показывает отсутствие/добавление, не угадывает связь. Сравниваются порядок услуг, имена, количества, роли включения, клиентские цены, единицы и клиентские описания/комментарии. Категории, приватные расходы, исключённые услуги и изменяющиеся подписанные URL фото не создают отличий. Фото отображаются, но не входят в diff.
- Представление получает явную allowlist клиентских полей. Это **не** публичный client API: полная внутренняя модель всё ещё доступна авторизованному сотруднику в браузере. Нет расходов, маржи, контактов или приватных заметок в самой таблице.
- Итог только PRIMARY; неизвестные цены явно не включены, «от» и RANGE остаются нижней границей. Разница бюджетов показывается только для двух полных фиксированных итогов, без обещания экономии на неполном составе.
- Переход из формы требует подтверждения потери несохранённых полей. Выбор варианта не меняет isRecommended/статус. Нативная печать из режима сравнения показывает инструкцию открыть клиентский вид, а не незаметно печатает другой активный вариант. Экспорт сравнительной таблицы отложен вместе с immutable export lifecycle.
- Это чистая проекция существующего read model без новых API, таблиц и миграций. Две ранее подготовленные миграции остаются обязательными перед выкладкой всей студии V2.

- Студия order synthetic QA: реальный pointer drag разделов/услуг, перенос в другой раздел, Escape без POST, undo/redo, стрелки клавиатуры, выбор раздела в инспекторе, мобильные кнопки, отсутствие overflow/page errors. - Студия comparison synthetic QA: выбор/лимит вариантов, только различия, смена точки сравнения, совпадающие варианты, unknown budget, отсутствие приватных полей в таблице, подтверждение выхода из dirty form, выбранный вариант в preview/editor, print guard, single-variant empty state и archived copy disabled. - Отдельный finish review по impeccable: композиция принята; исправлены draft preservation, отмена переключения раздела и изоляция печати. Подбор услуги получил вторичный стиль, чтобы не конкурировать с главным действием.
- SQL миграции проверен в изолированной транзакционной схеме PostgreSQL: существующее КП сохраняется, CHECK запрещает отсутствие/двух владельцев, перенос меняет owner без копирования, RLS/revoke закрывают прямой доступ anon/authenticated. Вся QA-схема откатана, отсутствие схемы проверено.
- Реальный Prisma/PostgreSQL service QA для третьего среза: удаление раздела, undo/redo/undo-redo, исходные ID и скрытые снимки, повтор UUID без повторного revision bump, обратная привязка ссылки переноса и неизменная revision сметы. SQL нового журнала проверен с RLS/revoke. Весь сценарий в изолированной схеме с безусловным rollback; отсутствие схемы после теста подтверждено. Это не тест production HTTP/auth/storage.
- Это **не** production E2E: новая схема проверена отдельно при подготовке релиза. Реальную авторизацию, storage и пользовательский сценарий нужно проверить после выкладки. Print media проверен визуально, но многополосный A4 PDF пока не принят отдельно.

## Безопасная выкладка

1. Зафиксировать backup БД и проверить текущее наличие таблиц/индексов.
2. После проверки предусловий применить только необходимые additive SQL: `prisma/migrations/20261007120000_standalone_proposals_v2/migration.sql`, затем `prisma/migrations/20261008120000_proposal_command_receipts/migration.sql`. Первая добавляет wrapper и nullable owner; вторая — закрытый серверный журнал. Существующие КП/услуги не удаляются.
3. Не выполнять вслепую `prisma migrate deploy`: журнал показывает много старых pending миграций, часть соответствующих таблиц уже существует. Отдельно сверить и восстановить журнал; не отмечать старые миграции applied без проверки SQL.
4. Проверить реальный временный черновик: создание → услуга → сохранение → открытие второй сессии → 409 → загрузка актуальной версии → клиентский вид → конвертация.
5. Пушить только согласованную production-ветку `master`, когда новая схема готова. Не выдавать preview за production.

### Релизный SQL для SQL Editor

`docs/sql/deploy_proposal_studio_v2.sql` объединяет обе исходные миграции без изменения DDL в одну транзакцию с `search_path=public`, `lock_timeout=5s` и `statement_timeout=120s`. Запускается целиком один раз после backup; при ошибке откатывается целиком. Не изменяет старые данные и журнал `_prisma_migrations`. Успешный результат — `STUDIO_V2_SCHEMA_READY`.

Повторная проверка релиза: `npm run build` PASS; 41 файл / 230 тестов PASS. `node --env-file=.env.local .impeccable/review/proposal-migration-qa.cjs` подтверждает точное совпадение DDL в bundle, сохранность существующих КП и customer merge, ограничения владельца и UUID журнала, RLS/revoke обеих новых таблиц. Проверка выполняется в отдельной схеме с полным rollback, без изменений рабочей схемы.

08.10.2026 пользователь применил bundle через SQL Editor и подтвердил `STUDIO_V2_SCHEMA_READY`. Read-only проверка `.impeccable/review/proposal-release-preflight.cjs` затем подтвердила в рабочей `public` обе таблицы, необходимые поля, 11 индексов, шесть валидированных ограничений, RLS/revoke и чтение через Prisma. Журнал старых миграций не изменялся; `prisma migrate deploy` не запускался. Это снимает schema gate для push в `master`, но не заменяет production HTTP/auth/storage E2E.

## Следующие этапы (не реализованы этим срезом)

1. Каталог V2: редактирование контактов, история цен в инспекторе, расширенные фильтры по контексту мероприятия, улучшенные проверки дублей/данных. Пагинация списка подрядчиков и launch с услуги уже реализованы; отдельная пагинация услуг одного подрядчика пока не нужна текущему UI и не добавлена.
2. Цена RANGE: snapshot верхней границы и полноценная интервальная арифметика; сейчас используется нижняя граница с явным «от».
3. Optimistic batch queue, scoped capture без чтения полного дерева, осознанное сравнение/слияние конфликтов и presence/polling. Undo/redo, UUID receipts/retry и безопасное локальное восстановление явных форм уже реализованы.
4. Шаблоны структуры и полноценный preflight: фотографии, свежесть и срок цены, гостевые ограничения, доступность. Базовый next-step уже реализован, но не объявляет КП готовым к отправке.
5. Durable клиентский snapshot/API, серверный PDF, безопасные ссылки и журнал экспортов. Сегодня клиентский вид предназначен для внутреннего сотрудника; полная внутренняя модель остаётся в его браузере.
6. Корпоративный PPTX adapter после получения шаблона и готового примера; официальная генерация презентаций пока не подключена.

Спецификация: `docs/EVENT_PROPOSAL_WORKSPACE_V2_SPEC.md`. Архитектура: ADR 014 и ADR 015.
