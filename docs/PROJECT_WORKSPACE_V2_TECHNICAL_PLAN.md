# Project Workspace V2 — технический план модульной карточки проекта

**Статус:** кодовый срез завершён; ожидает ручную миграцию и Preview-приёмку  
**Дата:** 2026-08-28  
**Реализация:** готовы аддитивный foundation, создание проекта, самостоятельная 12-колоночная сетка текущих модулей и атомарная настройка команды/layout с защитой revision/409  
**Основной ADR:** [`brain/decisions/012-modular-project-workspace.md`](../brain/decisions/012-modular-project-workspace.md)

## 1. Назначение документа

Этот документ — единая опора для поэтапной пересборки проектов. Он должен позволить продолжать работу после пауз и смены контекста без повторного проектирования и без догадок.

Главная цель: превратить проект из длинной фиксированной формы в гибкое рабочее пространство, которым удобно пользоваться и для короткого расчёта, и для крупного мероприятия с 50–70 строками сметы, задачами, файлами, таймингом и заметками.

План намеренно отделяет:

- бизнес-данные проекта;
- компоновку интерфейса;
- свободные рабочие материалы;
- механизм сохранения;
- перенос существующих данных.

Это нужно, чтобы изменение размера или скрытие виджета никогда не меняло сумму проекта, не удаляло заявку и не влияло на аналитику.

## 2. Подтверждённые продуктовые решения

1. Фиксированных типов проекта «маленький / средний / большой» не будет.
2. Проект собирается из модулей при создании и может быть перекомпонован позднее.
3. В шапке проекта всегда находятся основные данные и компактные финансы. Шапка не является виджетом.
4. `Смета` и `Заявки` — обязательные модули каждого полноценного проекта.
5. Остальные модули опциональны: задачи, свободная доска, тайминг, файлы, контакты, заметки, история и другие модули из реестра.
6. Модули имеют разрешённые размеры и перетаскиваются в режиме настройки.
7. Скрытие модуля не удаляет его доменные данные. Повторное добавление возвращает прежнее содержимое и настройки.
8. Ответственный выбирается при создании и может быть переназначен. Создатель больше не становится ответственным неявно.
9. У проекта есть участники. Ответственный всегда входит в их число.
10. Смета остаётся типизированной финансовой системой, но получает табличный UX: клавиатура, вставка диапазонов, массовые операции и автосохранение.
11. Свободная доска на первой итерации — ограниченное модульное пространство, а не полный клон Miro.
12. Задачи на доске ссылаются на существующие `WorkTask`, а не копируют их.
13. Текущую независимую смету нельзя одновременно переписывать вместе с карточкой проекта. Сначала новый UX проходит проверку на проектах, затем переиспользуется отдельно.

## 3. Что сейчас мешает работе

### 3.1. Фиксированная карточка

Текущая страница проекта всегда показывает одинаковый набор крупных блоков. Контакты, резюме, файлы или тайминг занимают место даже тогда, когда конкретному проекту не нужны. Порядок и размер нельзя адаптировать под сценарий.

### 3.2. Тяжёлая смета

Карточное представление плохо масштабируется до 50–70 строк. Пользователь много листает, теряет контекст колонок и не может работать привычными табличными приёмами.

### 3.3. Дорогие сохранения

Текущая страница после части PATCH-операций повторно загружает большой read model проекта. В результате блоки схлопываются, интерфейс меняет высоту, позиция прокрутки и фокус теряются. Даже быстрое исправление воспринимается как отдельная форма с отправкой.

### 3.4. Неявное владение

`Project.ownerUserId` всегда заполняется текущим пользователем при создании. Участников проекта как отдельной модели нет, поэтому невозможно надёжно построить «мои проекты» и отличить создателя от ответственного.

### 3.5. Риск дублирования источников истины

Если хранить содержимое существующих модулей внутри JSON виджета, появятся две версии сметы, задач или заявок. Это запрещено целевой архитектурой.

## 4. Границы и нецели

В рамках Project Workspace V2 не делаем:

- новый движок заявок, резерва, выдачи или приёмки;
- новую сущность задач вместо `WorkTask`;
- изменение формул сметы, комиссии, налога и маржи;
- автоматическую запись внешней финансовой сверки в проекты;
- полный бесконечный canvas уровня Miro с совместными курсорами;
- CRDT и одновременное посимвольное редактирование;
- хранение изображений и файлов в JSON или PostgreSQL;
- удаление старых проектных полей и таблиц в первой волне;
- одновременный редизайн независимых смет до проверки проектной таблицы;
- будущий блок проектов на главном дашборде — модель участников только готовит для него данные.

## 5. Инварианты, которые нельзя нарушать

### 5.1. Проекты и заявки

- Один `Project` связан с несколькими `Order` через существующий `Order.projectId`.
- Заявка без проекта продолжает работать как сейчас.
- Статус, резерв, выдача и приёмка живут в `Order`/`OrderLine`.
- Один реквизитный раздел сметы связан с одной заявкой.
- Demo-заявка остаётся `ProjectDraftOrder`; материализация в настоящую заявку выполняется в существующей `Serializable`-транзакции согласно ADR 006.
- Архивный проект остаётся read-only, пока отдельное решение явно не разрешит иное.

### 5.2. Финансы

- Канонические формулы остаются в общих helpers/read models, а не в компонентах таблицы.
- Серверный read model, XLSX и аналитика должны получать те же значения, что и UI. Исторический route с именем `/estimate/pdf` фактически отдаёт XLSX.
- Пользовательская вспомогательная колонка не участвует в аналитике, пока не сопоставлена с разрешённым каноническим полем и не прошла валидацию.
- Внешние финансовые снимки остаются неизменяемыми данными сверки согласно ADR 008.

### 5.3. Файлы

- В PostgreSQL находятся только метаданные и связи.
- Содержимое файлов остаётся в Supabase Storage.
- Виджет файлов показывает существующие `ProjectFolder`/`ProjectFile`; он не копирует файлы.

### 5.4. Задачи

- Виджет задач показывает существующие `WorkTask` с `projectId`.
- Изменение задачи из проекта видно в YouGile и наоборот.
- Скрытие виджета задач не отвязывает и не удаляет задачи.

### 5.5. Написание бренда

В пользовательских текстах используется `Grinvich`. Технические идентификаторы, enum и имена существующих API не переименовываются.

## 6. Целевая информационная архитектура

### 6.1. Фиксированная шапка

Шапка находится над сеткой и всегда содержит:

- название проекта;
- заказчика;
- статус и «мяч»;
- даты мероприятия и признак подтверждения;
- ответственного;
- участников;
- блокеры/важный сигнал в компактном виде;
- итог клиенту, внутренние затраты, ожидаемую маржу;
- состояние связанных заявок;
- действия: сменить статус, архивировать, открыть режим настройки.

Финансовая сводка в шапке — read-only представление канонической основной сметы. Отдельный обязательный «финансовый виджет» не создаётся, чтобы не дублировать цифры.

### 6.2. Сетка модулей

На desktop применяется детерминированная 12-колоночная сетка.

Базовые ширины:

| Пресет | Колонки | Назначение |
|---|---:|---|
| S | 4 | компактная справочная карточка |
| M | 6 | половина рабочей области |
| L | 8 | основной модуль рядом с компактным |
| XL | 12 | таблица, доска или широкий рабочий модуль |

Высота задаётся не произвольными пикселями, а разрешёнными пресетами конкретного типа модуля. Реестр модуля определяет минимальную и максимальную высоту.

На tablet сетка преобразуется в 8 колонок, на mobile — в одну колонку. На мобильном сохраняется порядок модулей, но не desktop-координаты.

### 6.3. Режим настройки

Обычный режим не показывает лишние ручки управления. Кнопка «Настроить пространство» включает:

- drag-and-drop модулей;
- изменение разрешённого размера;
- добавление модуля из каталога;
- скрытие опционального модуля;
- восстановление скрытого модуля;
- отмену последнего изменения раскладки;
- явный выход из режима.

`Смета` и `Заявки` закреплены: их можно перемещать и менять в допустимых пределах, но нельзя скрыть в первой версии.

### 6.4. Создание проекта

Окно создания состоит из двух частей.

Обязательные данные:

- название;
- существующий заказчик или новое название заказчика;
- ответственный;
- участники;
- при наличии — даты и стартовый статус.

Ниже отображается визуальный каталог модулей. Карточки разного размера показывают не только название, но и пользу модуля. `Смета` и `Заявки` уже выбраны и заблокированы от снятия. После создания открывается готовая стартовая раскладка, которую можно сразу поправить.

Создание проекта, участников, обязательных виджетов, папок по умолчанию и записи журнала выполняется одной короткой транзакцией.

## 7. Реестр модулей

Реестр — кодовая конфигурация, а не набор произвольных записей из БД. Она определяет контракт каждого типа.

Минимальный контракт:

```ts
type ProjectWidgetDefinition = {
  type: string;
  schemaVersion: number;
  title: string;
  description: string;
  icon: string;
  singleton: boolean;
  mandatory: boolean;
  allowedWidths: Array<4 | 6 | 8 | 12>;
  allowedHeights: string[];
  defaultSize: { width: number; height: string };
  permissions: "WOWSTORG_ONLY";
  dataSource: string;
  loadStrategy: "eager" | "lazy";
};
```

Планируемые модули:

| Тип | Обязательный | Источник истины | Первая версия |
|---|---|---|---|
| `ESTIMATE` | да | `ProjectEstimateVersion/Section/Line` | полный |
| `ORDERS` | да | `Order` | полный |
| `TASKS` | нет | `WorkTask` | полный |
| `FREE_BOARD` | нет | `ProjectWorkspaceItem` | базовый |
| `SCHEDULE` | нет | `ProjectScheduleDay/Slot` | обёртка текущего |
| `FILES` | нет | `ProjectFolder/ProjectFile` | обёртка текущего |
| `CONTACTS` | нет | `ProjectContact/CommunicationEntry` | обёртка текущего |
| `NOTES` | нет | существующие поля + структурированные заметки позднее | базовый |
| `HISTORY` | нет | `ProjectActivityLog` | полный read-only |

Новый тип модуля добавляется только вместе с:

- записью в реестре;
- Zod-схемой `config`;
- ограничениями размеров;
- empty/loading/error states;
- правами;
- правилами миграции `schemaVersion`;
- тестом реестра.

Неизвестный тип или неподдерживаемая версия не должны ломать страницу: показывается компактная карточка «Модуль временно недоступен» с техническим идентификатором для диагностики.

## 8. Предлагаемая модель данных

Названия ниже — целевой контракт. Перед миграцией их нужно повторно сверить с актуальной `prisma/schema.prisma`.

### 8.1. Изменения `Project`

```prisma
model Project {
  // существующие поля
  createdByUserId String
  createdBy       User   @relation("project_created_by", fields: [createdByUserId], references: [id], onDelete: Restrict)
  revision        Int    @default(0)

  members ProjectMember[]
  widgets ProjectWidget[]
}
```

- `ownerUserId` сохраняется и становится каноническим ответственным.
- `createdByUserId` фиксирует автора отдельно.
- `revision` используется только для составных изменений проекта; дочерние сущности имеют собственные ревизии.

Миграция выполняется безопасно: nullable поле → backfill из `ownerUserId` → проверка `NULL = 0` → `NOT NULL`.

### 8.2. Участники

```prisma
enum ProjectMemberRole {
  EDITOR
  VIEWER
}

model ProjectMember {
  projectId String
  userId    String
  role      ProjectMemberRole @default(EDITOR)
  addedById String
  createdAt DateTime @default(now())

  @@id([projectId, userId])
  @@index([userId, projectId])
}
```

Правила:

- участниками могут быть только активные пользователи WOWSTORG;
- ответственный обязательно является участником;
- смена ответственного и добавление его в участники атомарны;
- удалить текущего ответственного из участников нельзя;
- создатель не обязан навсегда оставаться участником, но остаётся в аудите;
- архивирование пользователя не удаляет историческое участие.

### 8.3. Компоновка виджетов

```prisma
model ProjectWidget {
  id            String   @id
  projectId     String
  instanceKey   String
  type          String   @db.VarChar(50)
  schemaVersion Int      @default(1)
  sortOrder     Int      @default(0)
  x             Int      @default(0)
  y             Int      @default(0)
  width         Int
  heightPreset  String   @db.VarChar(30)
  config        Json?
  isVisible     Boolean  @default(true)
  revision      Int      @default(0)
  createdById   String
  updatedById   String
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@unique([projectId, instanceKey])
  @@index([projectId, isVisible, sortOrder])
}
```

`id` генерируется клиентом до optimistic insert. Для singleton-модулей `instanceKey = type`; для будущих повторяемых модулей используется `type:<client-id>`.

В `config` разрешены только настройки отображения модуля. Смета, заявки, задачи, контакты и файлы в `config` не хранятся.

### 8.4. Элементы свободной доски

```prisma
model ProjectWorkspaceItem {
  id                String   @id
  projectId         String
  widgetId          String
  type              String   @db.VarChar(40)
  x                 Int
  y                 Int
  width             Int
  height            Int
  zIndex            Int      @default(0)
  payload           Json?
  linkedTaskId      String?
  linkedOrderId     String?
  linkedFileId      String?
  linkedSectionId   String?
  revision          Int      @default(0)
  createdById       String
  updatedById       String
  deletedAt         DateTime?
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@index([projectId, widgetId, deletedAt])
  @@index([linkedTaskId])
  @@index([linkedOrderId])
}
```

Разрешённые типы первой версии:

- текстовая заметка;
- стикер;
- заголовок;
- чек-лист;
- ссылка;
- изображение/файл как ссылка на `ProjectFile`;
- ссылка-карточка на `WorkTask`;
- ссылка-карточка на `Order`;
- фрагмент сметы как ссылка на section/line;
- группа/рамка.

`payload` валидируется discriminated union в Zod. Raw HTML, base64-файлы и произвольный исполняемый код запрещены.

Удаление элемента сначала мягкое (`deletedAt`), чтобы работали undo и восстановление. Физическая очистка — отдельная будущая фоновая задача с периодом хранения.

### 8.5. Идемпотентные операции

Для надёжного повтора структурных мутаций рекомендуется небольшая таблица receipt:

```prisma
model ProjectMutationReceipt {
  id          String   @id @default(cuid())
  projectId   String
  actorUserId String
  mutationId  String
  kind        String
  result      Json?
  createdAt   DateTime @default(now())

  @@unique([projectId, actorUserId, mutationId])
  @@index([createdAt])
}
```

Она нужна для create/delete/reorder batch и сетевых повторов. Обычный PATCH с явным конечным значением остаётся идемпотентным сам по себе. Старые receipts очищаются по безопасной retention-политике после появления фоновой уборки.

## 9. Свободная доска: разумный объём V1

### 9.1. Что должно быть

- ограниченное рабочее поле внутри виджета;
- сетка и привязка к направляющим;
- перемещение и изменение размера элементов;
- выбор нескольких элементов;
- копирование/дублирование;
- группировка;
- zoom в разумном диапазоне;
- undo/redo текущей сессии;
- вставка текста, ссылок и изображений;
- карточки-ссылки на задачи и заявки;
- понятный режим mobile read-only/упрощённого редактирования.

### 9.2. Чего не должно быть в V1

- бесконечного мира;
- стрелок и сложных блок-схем;
- совместных курсоров;
- комментариев на каждом пикселе;
- тяжёлых превью файлов;
- дублирования полной сущности задачи внутри доски.

Для canvas/grid-библиотеки решение принимается отдельным spike. В текущих зависимостях нет зрелого layout/canvas-пакета; писать drag/resize с нуля без сравнительного прототипа нельзя. Критерии выбора: React 19/Next 16, размер bundle, touch, accessibility, controlled state, отсутствие обязательного облака, активная поддержка и лицензия.

## 10. Смета как таблица, но не произвольная электронная таблица

### 10.1. Канонические колонки

Колонки имеют стабильные идентификаторы и типы:

- название;
- описание;
- тип строки;
- единица;
- количество;
- дни;
- цена клиенту за единицу;
- сумма клиенту;
- внутренняя стоимость;
- способ/статус оплаты;
- комментарий и реквизиты подрядчика.

UI может менять порядок, ширину и видимость, но не смысл поля.

### 10.2. Табличные возможности

- редактирование без открытия карточки;
- Enter/Tab/стрелки;
- вставка прямоугольного диапазона из Excel/Google Sheets;
- копирование диапазона;
- протягивание значения или формулы там, где это безопасно;
- массовое удаление/перемещение;
- вставка строк над/под выбранной;
- sticky header и закреплённые ключевые колонки;
- сворачиваемые секции;
- фильтр и быстрый поиск;
- undo/redo;
- виртуализация при больших сметах;
- сохранение фокуса и scroll position.

### 10.3. Вспомогательные колонки

После стабилизации основной таблицы можно добавить пользовательские колонки отдельными сущностями `ProjectEstimateCustomColumn` и `ProjectEstimateCustomCell`. Они имеют тип `TEXT | NUMBER | DATE | CHECKBOX | FORMULA`.

Ограничения:

- кастомные колонки по умолчанию не участвуют в итогах;
- формулы работают только с whitelisted функциями и ссылками на стабильные column keys;
- формулы не исполняют JavaScript;
- изменение порядка колонок не меняет формулу;
- экспорт явно маркирует пользовательские поля;
- сопоставление с финансовым полем требует отдельного подтверждённого сценария.

### 10.4. Общий расчётный слой

До нового grid UI нужно зафиксировать contract tests вокруг:

- `project-estimate-totals`;
- `estimate-read-model`;
- `estimate-xlsx`;
- XLSX вариантов client/internal (через исторический route `/estimate/pdf`);
- аналитики и work queue financials;
- преобразования независимой сметы в проект.

Новый UI отправляет бизнес-поля в существующую нормализованную модель. Формулы не переносятся в браузер как новый источник истины.

## 11. API-контракты

Все новые handlers используют `requireRole`, Zod и `jsonError`. В первой версии доступ — только WOWSTORG.

### 11.1. Создание проекта

`POST /api/projects` расширяется:

```json
{
  "title": "Проект",
  "customerId": "...",
  "ownerUserId": "...",
  "memberUserIds": ["..."],
  "eventStartDate": null,
  "eventEndDate": null,
  "widgets": [
    { "type": "ESTIMATE", "width": 12, "heightPreset": "table" },
    { "type": "ORDERS", "width": 12, "heightPreset": "standard" },
    { "type": "TASKS", "width": 6, "heightPreset": "tall" }
  ]
}
```

Сервер:

1. проверяет заказчика, активного ответственного и участников;
2. принудительно добавляет ответственного в members;
3. принудительно добавляет обязательные модули;
4. нормализует layout через единый validator;
5. создаёт проект, members, widgets, папки и activity log транзакционно;
6. возвращает готовый workspace read model.

### 11.2. Предлагаемые ресурсы

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/projects/[id]/workspace` | шапка, layout и лёгкие summary модулей |
| PATCH | `/api/projects/[id]/members` | ответственный/участники атомарно |
| PATCH | `/api/projects/[id]/widgets/layout` | batch раскладки с revision |
| POST | `/api/projects/[id]/widgets` | добавить/восстановить модуль |
| PATCH | `/api/projects/[id]/widgets/[widgetId]` | видимость/config/размер |
| POST | `/api/projects/[id]/workspace/items/batch` | create/update/delete элементов доски |
| POST | `/api/projects/[id]/estimate/batch` | атомарный набор табличных операций |

Не нужно возвращать содержимое всех тяжёлых модулей одним ответом. `workspace` отдаёт каркас; смета, файлы, история и canvas загружаются собственными endpoints при появлении в viewport или открытии.

### 11.3. Формат мутации

```json
{
  "mutationId": "uuid",
  "expectedRevision": 12,
  "operations": [
    { "op": "set", "entityId": "...", "field": "title", "value": "Новое значение" }
  ]
}
```

Успех возвращает изменённые сущности и новые revision, но не весь проект. Конфликт возвращает `409`, актуальную серверную revision и минимальный server snapshot для rebase.

## 12. Клиентская архитектура и сохранение

### 12.1. Разделение компонентов

Страница проекта не должна снова стать одним файлом на несколько тысяч строк. Целевые слои:

- `ProjectWorkspacePage` — initial data и границы маршрута;
- `ProjectHeader` — шапка;
- `ProjectWorkspaceGrid` — раскладка;
- `ProjectWidgetFrame` — общий chrome/loading/error/edit controls;
- `project-widget-registry` — определения и lazy imports;
- отдельный компонент каждого виджета;
- `ProjectWorkspaceStore` — локальное состояние и revisions;
- `ProjectMutationQueue` — отправка и повтор мутаций;
- `ProjectEstimateGrid` — таблица;
- `ProjectFreeBoard` — свободная доска.

### 12.2. Optimistic UI

Каждое пользовательское действие отражается локально сразу. В шапке показывается ненавязчивое состояние:

- `Сохранено`;
- `Сохраняем…`;
- `Нет сети — изменения в очереди`;
- `Не удалось сохранить — повторить`.

Запрещено блокировать всю страницу общей загрузкой после изменения одной строки.

### 12.3. Очередь мутаций

Очередь ведётся на уровне сущности, а не всей страницы:

- последовательные изменения одной ячейки выполняются FIFO или схлопываются до последнего значения до отправки;
- структурные операции add/delete/move не схлопываются;
- быстрые toggle отправляют явное конечное значение, а не команду `toggle`;
- ответ старой мутации не может перетереть более новое локальное значение;
- новый объект получает client ID до запроса, поэтому последующая правка может ссылаться на него;
- сетевой retry использует тот же `mutationId`;
- ошибка одной сущности не откатывает независимые успешные правки.

Рекомендуемый debounce для текста: 400 мс, flush при blur, Enter и уходе со страницы. Числовые финансовые поля сохраняются после валидного значения; незавершённый ввод остаётся локальным до подтверждения.

### 12.4. Защита от потери данных

- `beforeunload` предупреждает только при реально незафиксированной очереди;
- очередь и черновики восстанавливаются из IndexedDB (localStorage допустим только для очень малого fallback);
- ключ backup включает userId, projectId и schema version;
- после успешного acknowledgement запись удаляется;
- backup не содержит секретов и бинарных файлов;
- конфликт не стирает пользовательский ввод: предлагается применить локальное, принять серверное или посмотреть различия.

### 12.5. Два пользователя и realtime

CRDT не нужен. Используются:

- `revision`/`updatedAt`;
- оптимистические мутации;
- выборочная подписка или короткий polling только на summary/layout/tasks;
- revalidation при focus/visibility;
- правило: входящее событие с revision ниже или равной локальной игнорируется;
- dirty entity не заменяется realtime-снимком до разрешения очереди.

## 13. Next.js и производительность

- Маршрут отдаёт лёгкий initial shell и доступные данные шапки.
- Тяжёлые виджеты загружаются через lazy boundary.
- Каждый виджет имеет собственный skeleton той же геометрии, чтобы layout не прыгал.
- Ошибка одного виджета ловится локальной error boundary.
- Таблица виртуализирует строки после подтверждённого порога; типичный проект 50–70 строк не должен ощущать виртуализацию.
- Canvas не загружается, если модуль отсутствует или ниже viewport.
- Не добавлять тяжёлую библиотеку без bundle comparison в spike.
- Не использовать `router.refresh()` как подтверждение обычного cell edit.

Целевые метрики для проверки на preview:

- optimistic feedback: до 100 мс;
- acknowledgement обычной мутации p95: до 1,5 с при нормальной сети;
- отсутствие layout shift после сохранения;
- открытие существующего проекта не хуже текущей страницы;
- 70 строк сметы редактируются без заметных зависаний;
- 30 быстрых последовательных правок не теряются и приходят к тому же итоговому состоянию после reload.

## 14. Права и безопасность

- Все проектные API доступны только WOWSTORG.
- `ProjectMember` в V2 используется для продукта и фильтров, но не ослабляет текущую role-проверку.
- Сервер проверяет, что связанная задача, заявка, файл или section принадлежат тому же проекту.
- JSON payload имеет лимит размера и глубины.
- Текст очищается/экранируется; raw HTML запрещён.
- Файлы проходят существующие ограничения upload и bucket prefix.
- Архивный проект блокирует layout, board, estimate и member mutations на сервере, а не только в UI.
- Все значимые изменения пишутся в `ProjectActivityLog`; шумовые перемещения canvas можно агрегировать одной записью сессии, а не логировать каждый пиксель.

## 15. Миграция существующих проектов

### 15.1. Общий принцип

Миграция аддитивная и не удаляет старые данные. Так как владелец применяет миграции через Supabase SQL Editor, для каждой фазы необходимо подготовить:

1. идемпотентный или безопасно повторяемый SQL;
2. предварительные SELECT-проверки;
3. SQL валидации после применения;
4. описание отката;
5. порядок `SQL → deploy code → flag`.

Vercel deploy не применяет Prisma migrations автоматически.

### 15.2. Backfill

Для каждого существующего проекта:

- `createdByUserId = ownerUserId` как честное историческое приближение;
- owner добавляется в `ProjectMember` как `EDITOR`;
- создаются виджеты `ESTIMATE` и `ORDERS`;
- виджеты текущих непустых модулей добавляются автоматически:
  - tasks, если есть `WorkTask`;
  - contacts, если есть контакты;
  - files, если есть файлы/папки;
  - schedule, если есть дни;
  - notes, если заполнены `openBlockers`/`internalSummary`;
  - history можно создать скрытым или компактным;
- исходные сущности не копируются.

Default layout должен быть детерминированной чистой функцией от набора модулей. Повторный backfill не создаёт дубли благодаря `@@unique([projectId, instanceKey])`.

### 15.3. Проверки после backfill

- число проектов без creator равно 0;
- каждый проект имеет owner-member;
- каждый FULL-проект имеет видимые `ESTIMATE` и `ORDERS`;
- нет неизвестных widget types;
- координаты и размеры проходят validator;
- количество `Order`, estimate lines, tasks, files и contacts не изменилось;
- финансовые итоги до и после включения V2 совпадают.

## 17. Feature flags и безопасный rollout

Нужны минимум два независимых флага:

- `PROJECT_WORKSPACE_V2_ENABLED`;
- `PROJECT_ESTIMATE_GRID_V2_ENABLED`.

Флаг проверяется на сервере, его значение передаётся клиенту как часть разрешённого read model. Если будут добавлены новые env, нужно обновить `.env.example` и `brain/reference/env-inventory.md` через `npm run brain:inventory`.

Старый интерфейс остаётся fallback до завершения parity-периода. Переключение обратно не требует rollback БД, потому что миграции аддитивны.

Рекомендуемый rollout:

1. только preview/test project;
2. один внутренний пользователь;
3. оба пользователя, но только новые проекты;
4. несколько существующих проектов;
5. все активные проекты;
6. после периода стабильности — V2 по умолчанию;
7. удаление legacy UI только отдельной задачей и новым подтверждением.

## 18. Этапы реализации

Каждая фаза должна помещаться в отдельный проверяемый deploy и заканчиваться зелёной сборкой.

### Фаза 0. Контракты и измерения

- добавить/расширить tests финансовых helpers, read model и XLSX;
- снять baseline загрузки страницы и размера bundle;
- зафиксировать regression fixtures для малого и 70-строчного проекта;
- сделать spike grid-layout/canvas/table libraries;
- выбрать библиотеки или обосновать собственный минимальный слой.

**Gate:** никаких UI-миграций до прохождения финансовых contract tests.

### Фаза 1. Ответственный, создатель и участники

- миграция creator/members/revision;
- backfill;
- расширение создания и редактирования проекта;
- activity log смены ответственного/участников;
- фильтры «ответственный / участник» на уровне API как задел.

**Приёмка:** ответственный выбирается, переназначается и всегда состоит в участниках; существующие проекты не потеряны.

### Фаза 2. Модель layout без нового визуала

- `ProjectWidget` и registry;
- default layout/backfill;
- API чтения и batch update;
- revision/conflict/idempotency tests;
- старый UI продолжает работать.

**Приёмка:** layout можно изменить API и восстановить без влияния на доменные данные.

### Фаза 3. Новый экран создания

- основные поля;
- выбор ответственного/участников;
- визуальный каталог модулей;
- preview стартовой раскладки;
- транзакционное создание.

**Приёмка:** обязательные модули невозможно пропустить, повторная отправка не создаёт дубль.

### Фаза 4. Workspace shell и обёртка текущих модулей

- новая шапка;
- grid shell;
- widget frame/skeleton/error boundary;
- существующие Orders, Tasks, Contacts, Files, Schedule, History внутри адаптеров без смены бизнес-логики;
- feature flag.

**Приёмка:** цифры и действия совпадают со старой карточкой, layout не прыгает.

**Состояние 2026-08-30:** существующие Tasks, Orders, Contacts, Estimate, Files, Schedule, Notes и History подключены как самостоятельные элементы 12-колоночной сетки без копирования доменных данных. Сохранённые порядок и ширина применяются к карточке, мобильная раскладка остаётся одноколоночной. Аварийные серверные rollout-переключатели `PROJECT_WORKSPACE_V2_ENABLED` и `PROJECT_ESTIMATE_GRID_V2_ENABLED` передаются через API read model; выключение возвращает фиксированную компоновку или карточную смету без rollback БД. URL-параметры `workspace=legacy|v2` позволяют точечно проверять оба режима. Первичная загрузка использует согласованный skeleton, отдельный error frame с повтором и защиту от запоздавших ответов параллельных запросов. Тяжёлые модули загружаются независимо и защищены локальными error boundaries.

### Фаза 5. Режим настройки

- drag/resize;
- каталог добавления;
- hide/restore;
- ограничения обязательных модулей;
- undo layout;
- responsive derivation.

**Приёмка:** перезагрузка точно восстанавливает порядок; скрытие не удаляет данные.

**Состояние 2026-08-30:** готов безопасный inline-режим настройки: owner/members, hide/restore, drag-перестановка, клавиатурные стрелки, разрешённые ширина и высотный пресет, undo несохранённой раскладки. Высотный пресет задаёт `min-height` и не обрезает длинное содержимое. Сохранение выполняется одной Serializable-транзакцией с `expectedRevision`; обязательные ESTIMATE/ORDERS принудительно остаются видимыми. Успешный ответ обновляет локальный read model без полного reload. На touch-устройствах надёжной альтернативой drag остаются кнопки перемещения.

### Фаза 6. Надёжное автосохранение

- local store;
- mutation queues;
- revisions/409;
- local backup/retry;
- status indicator;
- выборочное обновление без full reload.

**Приёмка:** тест быстрых действий и двух вкладок не теряет конечное состояние.

**Состояние 2026-08-30:** свободная доска использует coalescing-очередь с revisions, idempotency и offline recovery. Смета сохраняется строго последовательно: быстрые правки объединяются debounce-окном, устаревший ответ не помечает более новый черновик сохранённым, локальная копия остаётся в браузере, а общий reload после сохранения отсутствует. Сервер принимает полный нормализованный снимок одной `Serializable`-транзакцией и защищает его revision/CAS-проверкой; конфликт вкладок возвращает 409 и не перезаписывает более свежую версию. Вкладки дополнительно сообщают друг другу новую revision через `BroadcastChannel`: чистая вкладка обновляется автоматически, а вкладка с несохранённым черновиком останавливает autosave и предлагает явно принять серверную версию либо повторить сохранение подтверждённого локального черновика поверх свежей основы. Полный batch выбран намеренно вместо цикла из десятков отдельных Prisma-операций. Пустые новые строки и удаление всех разделов не приводят к тихой потере данных; автосохранение ставится на паузу до завершения ввода или ручного подтверждения. Автосохранения сметы не создают шумные Telegram-события.

### Фаза 7. Свободная доска

**Статус на 2026-08-29:** реализован вертикальный срез V1; миграция подготовлена, но намеренно не применена до завершения всей карточки.

- schema/items API;
- базовые элементы;
- task/order/file links;
- move/resize/group/undo;
- soft delete;
- лимиты и lazy load.

Реализовано: строгая схема элементов, batch API с idempotency/revisions, offline recovery, базовые и связанные блоки, move/resize, выбор и сохраняемая группировка, совместное перемещение группы, duplicate, undo/redo, soft delete и лимит 200 элементов. Визуальная браузерная приёмка остаётся после ручного применения общей миграции.

**Приёмка:** 200 элементов остаются отзывчивыми; файл хранится в Storage; связанная задача едина с YouGile.

### Фаза 8. Табличная смета

**Статус на 2026-08-30:** реализован совместимый табличный срез поверх существующей модели и финансовых формул; карточный режим сохранён как fallback.

- column registry;
- keyboard navigation;
- paste/batch;
- sticky/sections;
- virtualization;
- autosave queue;
- сравнение итогов V1/V2.

Реализовано: компактные редактируемые строки локальных разделов, переключение «Таблица / Карточки», переход Enter/Shift+Enter и стрелками вверх/вниз по одной колонке, вставка прямоугольного диапазона из Excel/Google Sheets с автоматическим созданием недостающих строк, sticky header, выбор строк, копирование выбранного диапазона в TSV, массовое дублирование/удаление и вставка строки над/под выбранной. Позиция страницы для каждой версии сметы сохраняется в пределах вкладки браузера и восстанавливается при возвращении к длинному проекту. Последовательное автосохранение работает без full reload; сервер сохраняет снимок атомарно и проверяет revision. Расчёт суммы строки и итогов по-прежнему проходит через существующие нормализаторы; parser/paste и финансовый parity UI/read model/XLSX покрыты unit-тестами, включая диапазон из 70 строк. Исторический endpoint с суффиксом `/estimate/pdf` фактически отдаёт XLSX; отдельного PDF-builder в текущем продукте нет. Следующий шаг — браузерная приёмка на 50–70 строках после применения общей миграции владельцем.

**Приёмка:** fixtures, UI, read model, XLSX и analytics используют канонический расчёт; 70 строк удобны без карточного скролла.

### Фаза 9. Пользовательские колонки и шаблоны layout

- helper columns/formulas с sandboxed grammar;
- сохранение собственных шаблонов проекта;
- «сохранить текущую раскладку как шаблон»;
- новые проекты из шаблона.

**Статус на 2026-08-30:** реализованы оба безопасных среза фазы.

Пользователь может сохранить текущую компоновку карточки как личный шаблон и выбрать его при создании проекта. Шаблон хранит только типы, порядок, видимость и допустимые размеры блоков; содержимое смет, заявок, файлов и свободной доски не копируется. Обязательные блоки `ESTIMATE` и `ORDERS` принудительно остаются включёнными.

В табличной проектной смете можно добавить до 12 вспомогательных колонок типов `TEXT`, `NUMBER`, `DATE`, `CHECKBOX`, `FORMULA`, задать им порядок и допустимую ширину. Определения колонок и неформульные значения ячеек входят в тот же атомарный revision-снимок, что и локальные строки. Формульные значения не сохраняются и вычисляются только из текущего снимка строки.

Грамматика формул не использует `eval` или JavaScript: разрешены арифметика, скобки, канонические read-only поля строки, стабильные ключи пользовательских колонок и функции `round`, `min`, `max`, `abs`. Есть защита от неизвестных полей, деления на ноль и циклических зависимостей. Вспомогательные значения не передаются в канонические financial helpers, аналитику и текущие PDF/XLSX; финансовая изоляция закреплена unit-тестом.

**Приёмка:** custom data не попадает в финансы без явного mapping.

### Фаза 10. Независимые сметы

- переиспользовать проверенный `ProjectEstimateGrid`;
- сохранить отдельную сущность `StandaloneEstimate` согласно ADR 007;
- повторить parity и conversion tests.

**Статус на 2026-08-30:** табличный движок подключён к локальным разделам независимой сметы с сохранением карточного fallback. Отдельная сущность, существующий batch PATCH и финансовые формулы не менялись; проектные вспомогательные колонки в независимую смету не передаются. До закрытия фазы остаётся браузерная приёмка и повторный conversion/parity прогон после применения общей миграции владельцем.

**Приёмка:** быстрый расчёт не получает ненужную проектную карточку, но использует тот же табличный движок.

## 19. Тестовая стратегия

### 19.1. Unit

- registry и миграция config schema versions;
- layout normalization/packing;
- разрешённые размеры;
- обязательные модули;
- formula grammar;
- mutation coalescing/FIFO;
- revision merge;
- канонические финансовые формулы.

### 19.2. API/integration

- роль и архивный read-only;
- owner/member invariants;
- транзакционное создание;
- idempotency повторного запроса;
- conflict 409;
- same-project проверки linked entities;
- batch estimate partial failure: вся финансово связанная группа либо применяется, либо откатывается;
- backfill на копии схемы.

### 19.3. E2E

1. создать минимальный проект;
2. создать насыщенный проект с опциональными модулями;
3. переставить/изменить/скрыть/вернуть модуль;
4. назначить и сменить ответственного;
5. быстро добавить и изменить строки сметы;
6. вставить диапазон из Google Sheets;
7. связать задачу и изменить её из YouGile;
8. работать offline, восстановить сеть и проверить очередь;
9. открыть две вкладки и получить контролируемый конфликт;
10. архивировать и проверить server-side запрет;
11. открыть старый проект после backfill;
12. скачать client/internal XLSX и сравнить итоги;
13. проверить независимую смету и конвертацию после общей table-фазы.

### 19.4. Нагрузочные сценарии

- 70 и 300 строк сметы;
- 100 задач проекта;
- 200 элементов доски;
- 20 файлов без загрузки бинарных данных в initial response;
- 30 быстрых mutations одной сущности;
- 100 mutations разных строк;
- медленная сеть и один потерянный ответ.

### 19.5. Visual/a11y

- desktop/tablet/mobile;
- светлая/тёмная тема, если модуль её поддерживает;
- клавиатурное управление таблицей и layout controls;
- видимый focus;
- aria labels drag/resize alternatives;
- reduced motion;
- skeleton той же высоты;
- отсутствие горизонтального скролла страницы (таблица может иметь локальный контролируемый scroll).

## 21. Ёмкость Supabase

Снимок на 2026-08-28:

- PostgreSQL: около 22 MB;
- проектов: 26;
- строк проектных смет: 197;
- задач: 95;
- подзадач: 168;
- файлов в Storage: 227, около 75,6 MiB содержимого;
- ориентир текущего Free plan Supabase: 500 MB database и 1 GB Storage.

Это не гарантия будущей квоты; перед реализацией и перед production rollout значения нужно измерить повторно по актуальной документации Supabase.

Вывод:

- layout/members/revisions занимают мало;
- текстовые board items обычно дешевле файлов;
- главный рост даёт Storage, поэтому изображения нельзя помещать в JSON;
- даже 100 проектов × 300 элементов × условные 2 KB — около 60 MB payload до индексов и служебного overhead, но реальные размеры нужно измерить на staging;
- нужны лимиты: размер payload, число элементов на board, число custom columns и retention soft-deleted items/receipts.

## 22. Основные риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Разъезд UI/read model/XLSX/аналитики | критичное | общий расчётный слой + contract/parity tests |
| Потеря быстрых правок | высокое | per-entity FIFO, explicit values, revisions, receipts, local backup |
| Дублирование данных в widget config | критичное | config только для отображения, доменные adapters |
| Поломка старых проектов | высокое | аддитивная миграция, deterministic backfill, legacy fallback |
| Слишком тяжёлый initial load | высокое | лёгкий shell, lazy widgets, независимые read models |
| Неуправляемый canvas | среднее | ограниченный V1, лимиты, library spike |
| Удаление данных при скрытии | высокое | `isVisible`, а не cascade delete |
| Конфликт двух пользователей | среднее | revision/409/rebase, не LWW вслепую |
| Большой bundle | среднее | lazy import и bundle budget |
| Переполнение DB/Storage | среднее | файлы в Storage, telemetry, лимиты, retention |
| Один огромный React-компонент | высокое | registry, adapters, store/mutation service, component boundaries |
| Слишком большой одновременный релиз | критичное | фазы, flags, deploy gate, rollback на каждом шаге |

## 23. Rollback

### До удаления legacy UI

1. выключить feature flag;
2. пользователи возвращаются на старую карточку;
3. новые таблицы остаются, но не влияют на старые данные;
4. не удалять миграцией creator/members/widgets во время инцидента;
5. если проблема только в estimate grid, отключить второй флаг независимо.

### При проблеме миграции

- остановить rollout до включения флага;
- выполнить validation queries;
- исправить backfill отдельной forward-only миграцией;
- не делать destructive rollback, если новые таблицы уже содержат пользовательские данные;
- экспортировать затронутые записи перед любым ручным исправлением.
